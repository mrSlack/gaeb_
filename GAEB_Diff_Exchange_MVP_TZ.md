# GAEB Diff & Exchange — техническое задание MVP

**Редакция:** 0.2, 26.10.2026  
**Продукт:** независимая веб-платформа для обмена GAEB-документами и сравнения версий Leistungsverzeichnis, Angebot и Auftrags-LV.  
**Основной пользователь:** подрядчик/калькулятор, работающий с заказчиками и программами типа RIB iTWO.  
**Статус:** проектное ТЗ; до завершения реализации необходимо проверить реальные тестовые файлы и протоколы импорта/экспорта.

## 1. Цели и границы

### 1.1. Цели
- Импорт GAEB DA XML 3.3 X83, X84, X86 (разрешать X84 только с привязкой к исходному LV либо с предупреждением об отсутствии контекста).
- Создание коммерческого предложения по X83, ввод Einheitspreise, корректный экспорт X84.
- Сравнение двух LV и трехстороннее сравнение `исходное X83` + `мое X84` + `новое X83/X86`.
- Наглядный diff структуры, позиций, объёмов, текстов, единиц измерения, цен, скидок/надбавок и их экономического влияния.
- Версионирование без перезаписи оригинальных импортов, отчет о расхождениях, история рассмотрения.
- Перенос своих цен в новую редакцию LV с подтверждением рисковых случаев.

### 1.2. Явно не входят в первый релиз
- Полноценный счетный модуль X89/X89B и XRechnung.
- X31 Aufmaß, полноценный Nachtragsmanagement, взаиморасчеты и ERP.
- GAEB 3.2, D/P-форматы, beta GAEB 3.4, прямое API-подключение к iTWO, мобильное приложение.
- Автоматическое юридическое заключение о Nachtrag и автоматическая замена договора.

### 1.3. Стандарты
- GAEB DA XML 3.3 (действующая редакция 2023-01). Для LV-пакета X83/X84/X86 применяется редакция схем 2021-05; изменение 2023-01 относится к X31.
- GAEB 3.4 (2026-03) существует как beta и не является основой MVP.
- Приемочные файлы и критерии BVBS GAEB XML 3.3, отдельные round-trip тесты в RIB iTWO.

## 2. Ключевые пользовательские сценарии

**US-01 Импорт:** пользователь загружает X83, система определяет фазу/версию по содержимому, валидирует XML/XSD, создает проект и неизменяемый снимок LV, показывает дерево разделов и позиции.

**US-02 Angebot:** по импортированному X83 создается расчетный набор цен. Пользователь вводит EP и требуемые Bietertextergänzungen, проверяет итоги, экспортирует X84, исходная OZ-Maske и специфика позиции не меняются.

**US-03 Новая редакция:** поступает X83 V2. Пользователь привязывает его к существующему проекту; система создает новый LV Snapshot, не удаляя V1.

**US-04 Diff LV-LV:** сравниваются X83 V1 и X83 V2. Выводятся добавленные/удаленные/перемещенные/измененные позиции, изменения Menge, Einheit, Kurz- и Langtext, Vorbemerkungen, признаков позиции и приложений.

**US-05 Трехсторонний diff:** исходный X83 V1 + наш X84 + новый X83 V2 либо X86 заказчика. Система показывает (а) изменения требований от заказчика, (б) изменение EP, только когда новые цены присутствуют, (в) прогноз суммы нового LV на старых EP как отдельный явно маркированный сценарий.

**US-06 Перенос EP:** для подтвержденно одинаковых позиций можно скопировать прежний EP. При изменениях текста, типа, единицы либо сомнительном сопоставлении копирование требует подтверждения. Для новых позиций EP пустой. Создается новая версия предложения, исходное не перезаписывается.

**US-07 Разбор расхождений:** эксперт отмечает изменения как `не проверено`, `принято к сведению`, `нуждается в уточнении`, добавляет комментарий; фильтрует по типу и значимости; выгружает PDF/XLSX отчет.

**US-08 Неполные файлы:** отдельный X84 без исходного X83 можно сохранить, но система не заявляет о полном сравнении структуры, пока пользователь не привяжет соответствующее LV.

## 4. Экран «Сравнение»

1. Заголовок: проект, имена загруженных файлов, дата, статус проверки, режим (LV↔LV, Angebot↔Auftrag, 3-way).
2. Сводка: количество новых, удаленных, измененных, перенумерованных и неоднозначных позиций; изменение Mengen/EP/GP и количество спорных изменений.
3. Панель фильтров: тип изменения, раздел, диапазон OZ, денежная значимость, подтверждение, только изменения текста.
4. Центральная таблица с закрепленными `OZ`, `Kurztext`; для каждой позиции рядом `было`, `стало`, `Δ` для Menge, ME, EP, GP.
5. Дерево разделов слева с количеством отличий.
6. Панель деталей справа: сравнение Langtext по абзацам/словам; вложения; происхождение значения; формула изменения; комментарий.
7. Действия: «Подтвердить соответствие», «Не сопоставлять», «Перенести EP», «Запросить уточнение», «Экспортировать diff».
8. Индикация: добавлено, удалено, изменено, без изменений, неуверенное сопоставление; не использовать один цвет без текстовой маркировки.
9. Прямая загрузка оригинальных файлов для независимой проверки.

**Принцип:** форма визуального отображения и XLSX/PDF отчеты — внутренний продуктовый формат, а не новая фаза GAEB.

## 5. Правила сравнения

### 5.1. Нормализация
- Валидация XML без DTD/XXE, безопасная обработка вложений и rich text.
- Определение фазы по структуре, а не только расширению файла.
- Данные отделяются по сущностям: `LV structural snapshot` и `Price Sheet`.
- Цены X84 связываются с исходным LV. Новый X83 может не содержать EP; этот факт сохраняется как `null`, не заменяется на 0.
- Исходный файл и необработанные поля/вложения хранятся для аудита и возможности доработки парсера.
- Семантическая нормализация не допускает потерь юридически значимых деталей и текста.

### 5.2. Матчинг позиций
Приоритет кандидатов: GUID (только при подтвержденном общем происхождении) → OZ + иерархия + тип → сравнение текста, единицы, соседних позиций и разделов. Высокая уверенность необходима для автоматического подтверждения. Переиспользованный OZ с иным содержанием помечается подозрительным. Split/merge, повторенные номера, неоднозначности — ручное разрешение; никогда не выбирать произвольно.

### 5.3. Сравниваемые поля
`oz`, `parent/section`, `order`, `node_type`, `position_type`, `short_text`, `long_text`, `quantity`, `unit`, `unit_price`, `line_total`, `percentage_markup`, `discount`, `bidder_completions`, `attachments`, `notes`, `alternative/basic/dependent links`, `currency`, `lv_headers/preliminaries` (по доступности в соответствующей фазе).

### 5.4. Финансовая оценка
Для обычной позиции `GP = Menge × EP` с формально установленными правилами округления. Разложение:
- эффект объема: `(M2 − M1) × EP1`;
- эффект цены: `M2 × (EP2 − EP1)`;
- общий эффект: сумма двух эффектов до округления.

Для примерной строки `100 м² × 45 EUR` против `120 м² × 42 EUR` разница +540 EUR, из них +900 EUR от объема и −360 EUR от цены. Для специальных видов позиций использовать специализированные расчеты, а при отсутствии стратегии честно показывать «сумма требует проверки», исключать из недостоверной агрегированной суммы.

### 5.5. Различение показателей
- `Original Bid`: фактическая сумма старой X84.
- `Repriced New Scope`: новая структура LV при переносе согласованных старых EP; исключительно прогноз.
- `Customer Price`: реальные новые цены, если они переданы в X86/ином контекстном документе.
- `Unknown`: поле отсутствует. Никогда не приравнивать неизвестное к нулю.

### 5.6. Изменение одного поля не означает принятие другого
Перенос EP при измененном Langtext, единице или типе позиции должен быть подтвержден. Изменения в исходном X83 не редактируются в экспортируемой X84, кроме предназначенных фазой данных предложения. Новая X84 создается от нового исходного X83.

## 6. Данные и связи

Реализационная схема в `gaeb_diff_initial_schema.sql`. Концептуальные сущности:

| Таблица | Смысл и ключевые поля |
|---|---|
| organizations, users, organization_memberships | изоляция компаний, пользователи, роли |
| projects | проект и контрагент |
| gaeb_documents | оригинал загрузки, SHA256, GAEB phase/version/edition, storage key, validation report |
| lv_snapshots | неизменяемая структурная редакция LV, источник и предыдущая редакция |
| lv_nodes | разделы, заголовки и позиции с родительской иерархией, OZ, GUID, текстами, Qty, ME, типом |
| price_sheets | набор цен: наше предложение, предложенные заказчиком цены, модельный прогноз |
| price_entries | EP, GP, скидки, bidder completions, прочие ценовые поля на отдельную позицию |
| comparisons | контекст сравнения: исходная версия, левая и правая редакции, левый/правый наборы цен, версия diff-правил |
| comparison_matches | пары сопоставленных позиций, способ сопоставления, уверенность, ручное подтверждение |
| comparison_changes | конкретное измененное поле, значения, тип, влияние на сумму, необходимость проверки |
| review_comments, audit_events | решения пользователя, комментарии и полный след действий |

Нужные индексы: `(snapshot_id, oz)`; `(snapshot_id, source_guid)`; `(comparison_id, match_status)`; `(comparison_id, change_type)`; `document SHA256`. Все бизнес-запросы и операции — в рамках `organization_id`/`project_id` и авторизации.

## 7. Архитектура

**Frontend:** React, TypeScript, TanStack Table/virtualized rows, rich text diff, аутентификация OIDC.  
**Backend:** FastAPI, Pydantic, PostgreSQL, SQLAlchemy/Alembic.  
**GAEB layer:** версии схем XSD, `lxml` (DTD/XXE disabled), phase-specific adapters, deterministic canonical model.  
**Diff layer:** pure comparison engine with deterministic rules, matching suggestions, monetary calculation strategies.  
**Tasks:** Redis + RQ/Celery (импорт и сравнение в фоновой серверной очереди).  
**Storage:** object storage S3-compatible with immutable original files and backup.  
**Deployment:** EU/Germany hosting, containers, TLS, backups, logging/metrics.

Критично: `parser_version`, `schema_version` и `diff_rules_version` записываются при каждой операции для воспроизводимости результатa. Смена алгоритма запускает новую comparison run, но не стирает предыдущую.

| Method | URL | Назначение |
|---|---|---|
| POST | `/api/v1/projects` | создать проект |
| POST | `/api/v1/projects/{id}/documents` | загрузить GAEB |
| GET | `/api/v1/projects/{id}/documents` | файлы и статусы |
| GET | `/api/v1/documents/{id}/validation` | предупреждения парсера/XSD |
| GET | `/api/v1/snapshots/{id}/nodes` | пагинированное дерево и позиции |
| POST | `/api/v1/price-sheets` | новый набор цен |
| PATCH | `/api/v1/price-sheets/{id}/entries/{nodeId}` | обновить EP/данные предложения |
| POST | `/api/v1/comparisons` | запуск 2-way/3-way diff |
| GET | `/api/v1/comparisons/{id}` | сводка diff, статусы и вычисления |
| GET | `/api/v1/comparisons/{id}/changes` | фильтры/пагинация/сортировка |
| PATCH | `/api/v1/comparisons/{id}/matches/{id}` | подтвердить/отклонить соответствие |
| POST | `/api/v1/comparisons/{id}/carry-forward` | создать новый price sheet с подтвержденным переносом EP |
| POST | `/api/v1/price-sheets/{id}/exports/x84` | выгрузка X84 |
| GET | `/api/v1/comparisons/{id}/report?format=xlsx` | отчет XLSX/PDF |

Пример запроса на сравнение:

```json
{
  "mode": "THREE_WAY",
  "base_snapshot_id": "uuid-x83-v1",
  "left_snapshot_id": "uuid-x83-v1",
  "left_price_sheet_id": "uuid-own-x84",
  "right_snapshot_id": "uuid-new-x83-or-x86",
  "right_price_sheet_id": null,
  "projection": "REPRICE_WITH_CONFIRMED_LEFT_EP"
}
```

`right_price_sheet_id = null` означает отсутствие цен заказчика. Результат прогноза обязан называться прогнозом, а не ценой заказчика.

## 9. Нефункциональные требования

- Обработка до 10 тыс. позиций на LV как целевой профиль MVP; большие файлы — через job и отображение прогресса.
- Целевые показатели для стенда с 10 тыс. обычных позиций: импорт ≤ 30 с, diff ≤ 20 с при достаточных ресурсах; подтверждаются нагрузочным испытанием, не обещаются без него.
- UI-таблица виртуализирована, сортировка/фильтрация серверные; не загружать тысячи тяжелых rich-text блоков одновременно.
- Контроль 2FA/SSO по конфигурации, RBAC, аудит, шифрование в транзите/покое, EU storage, резервирование и восстановление.
- Ограничения размера файлов, лимиты ресурсов парсера, проверка MIME/phase, безопасный XML, антивирус и защита от zip/decompression bombs.
- Хранение исходников и экспортных файлов, запрет тихой перезаписи, идемпотентность по хэшу при повторных загрузках.
- Никакая «неизвестная цена» не превращается в 0 без явного действия пользователя.
- UI в первую очередь DE/RU (термины GAEB сохранять по-немецки), интерфейс доступен с клавиатуры, цвета дублируются текстовыми метками.

## 10. Приемочные тесты

**AT-01:** X83 с корректной фазой/версией импортируется с полным OZ, заголовками, позициями, Qty/ME, Kurz-/Langtext и приложениями. Неверный XML получает диагностическое сообщение; оригинал сохранен.

**AT-02:** тестовые материалы BVBS проверены по требованиям: Normal-/Bedarfs-/Grund-/Alternativposition, индексы OZ, графика в Langtext, предельное количество, Zuschlag, текстовые дополнения. Поддержка должна быть подтверждена либо явно заблокирована без искажения/тихой потери.

**AT-03:** экспорт X84 валиден в GAEBXML Checker и независимо читается целевой версией RIB iTWO; сохраняет OZ-Maske, иерархию, валюту, цены, дополнения и поддерживаемые специальные позиции. Тест не равен официальной сертификации.

**AT-04:** V1 100 м² → V2 120 м², EP 45 EUR: определяется ΔMenge +20 м², прогнозная разница +900 EUR.

**AT-05:** V1 100 м² × 45 EUR → V2 120 м² × 42 EUR: итог +540 EUR, отдельные эффекты +900 и −360 EUR.

**AT-06:** изменение Langtext без числа/цены видно в diff, финансовый эффект не изобретается.

**AT-07:** новая/удаленная позиция отображается отдельно; перенос EP в новые позиции автоматически запрещен.

**AT-08:** изменение OZ при идентичном содержании дает кандидат «перенумеровано»; одна и та же OZ с новым содержанием требует проверки; случайное повторное сопоставление отсутствует.

**AT-09:** X83 V2 без EP не получает ложных «цен заказчика»; доступен только сценарий прогноза на своих EP.

**AT-10:** после переноса EP V1 остается неизмененной; формируется новая X84 на основе X83 V2.

**AT-11:** два пользователя разных организаций не видят чужие документы/комментарии/расчеты даже при подмене URL или ID.

**AT-12:** diff-отчет включает базу сравнения, входные файлы/хэши, время, правила сопоставления, перечень нерешенных случаев и предупреждение о прогнозных суммах.

| 6 (нед. 11–12) | перенос EP, отчеты, комментарии | X84 V2 + протокол разногласий |
| 7 (нед. 13–16) | совместимость, безопасность, QA, пилот | приемочные тесты на реальных файлах |

Возможен урезанный внутренний proof-of-concept через 3–4 недели, но его нельзя считать совместимым GAEB-продуктом до проверки X84 с реальным iTWO.

## 12. Риски и открытые вопросы

- Реальная совместимость зависит от версии RIB iTWO, типов используемых позиций и оригинальных примеров.
- В X84 может не быть полного текста и Mengen — обязательна привязка к исходной X83.
- Сложные Zuschläge, Bedarfs-/Alternativposition и Bietertextergänzungen требуют отдельных round-trip тестов.
- XML 3.2 несовместим по синтаксису с 3.3, поддержку старых версий нельзя свести к замене версии.
- Некоторые изменения структуры невозможно однозначно сопоставить; обязательный ручной workflow.
- PDF diff-отчет юридически не заменяет подписанную договорную документацию.

## 13. Ближайшее техническое действие

Получить **три реальных файла одного проекта**: первоначальный X83, вашу соответствующую X84, измененный X83 или присланную X86. Обезличить их и прогнать через парсер/дифф-прототип. Это главный тест точности модели и реальной пользы для пользователя.
